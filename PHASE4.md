# Phase 4 — RAG End-to-End

Phase 4 adds retrieval-augmented generation to this product: a document Q&A
surface over real job descriptions, the user's resume, and their application
notes. It is built into `job-pipeline`, not as a separate app. Theory was
studied 2026-10-17 → 2026-10-22 (revision notes in the Drive folder
`phase4-revision`, files `01` to `08`); progress tracking lives in the study
repository.

## How sessions work

- "Start part N" or "implement part N" in this repo means follow the matching
  checklist below.
- RAG is new to Protima. Before each part, explain in plain words what is being
  built and why, linked to the revision note it uses. Then give one small task
  at a time. Do not move on until the current task runs.
- Protima types the code. The coding agent explains, reviews, tests, and
  debugs unless explicitly asked to write it.
- Explain only the new layer (RAG, pgvector, the SDK call being added), not the
  FastAPI/React code around it that she already knows.
- Each part ends with something runnable, a test, and a commit, with this file
  updated in the same commit.

## Approach

Build a simple RAG end to end first (parts 1–5), so the whole flow is visible
once. Then measure it (part 6). Then improve one thing at a time and measure
again after each (parts 7–10), so every improvement has a number behind it.

## Target architecture

```text
Browser / Next.js (`web/`)  — Q&A screen with clickable citations
          |
          v
FastAPI application (`backend/`)
  ingestion:  document -> chunks -> embeddings -> Postgres (pgvector)
  question:   rewrite -> hybrid search (vector + full-text, RRF)
              -> metadata filter -> rerank -> answer with citations
  |            |              |             |          |
Postgres     OpenAI         OpenAI        Cohere     Mem0
+ pgvector   embeddings     generation    Rerank     (memory, in Postgres)
                             |
                          Langfuse
```

Postgres stays the single database: chunks, vectors, and metadata live next to
the existing `jobs`, `users`, and `applications` tables.

## Decisions (2026-10-26)

- **Corpus.** The 7 seeded jobs and one hard-coded profile are too small for
  retrieval to be meaningful or for eval numbers to say anything. Add about 100
  real jobs imported from Arbeitnow (the API the MCP server already uses), a
  per-user resume entered as pasted text (PDF upload later, if at all), and the
  user's application notes.
- **Vector store.** pgvector in the existing Postgres, not a separate vector
  database. Same database, same backups, same connection; the scale here is
  small.
- **Embedding model.** OpenAI, because the product already uses OpenAI. The same
  model must embed both stored chunks and questions.
- **Reranker.** A hosted API (Cohere Rerank). A self-hosted cross-encoder needs
  PyTorch, which does not fit Render's free instance.
- **Privacy.** Every retrieval query filters by `user_id` from the first search
  onward. One user's resume or notes must never reach another user's answer.

### 2 — Chunking

**Status:** Complete (2026-10-31)

**Build:** a chunking function. Structural for resumes (one chunk per section),
with recursive splitting inside any section that is too long; recursive with
overlap for job descriptions. Revision note `01`.

**Acceptance:** unit tests on real text; the chunks are printed and read by eye
before they are embedded.

**Implementation checklist:**

- [x] Version 1 hand-written first (paragraphs only, merged up to a limit) to
      understand what a recursive splitter does, then replaced by
      `langchain-text-splitters` `RecursiveCharacterTextSplitter`, the
      standard tool for the same algorithm (`backend/app/chunking.py`).
- [x] Size in tokens, not characters: `from_tiktoken_encoder` with
      `cl100k_base`, the tokenizer of OpenAI's embedding models. LangChain
      imports tiktoken but does not install it, so both are dependencies.
- [x] 300 tokens per chunk, 50 tokens of overlap. Separators
      `

`, `
`, `. `, ` `, `""`; the empty string lets a word longer
      than the limit (a long URL) still be cut. Starting values; Part 6
      measures them.
- [x] Decision: no separate structural splitter for resumes. A pasted resume
      separates its sections with blank lines, which is the splitter's first
      cut, so the same function serves jobs, resumes and notes.
- [x] `backend/tests/test_chunking.py`: 6 tests (limit, empty text,
      paragraph boundaries, overlap, a word longer than the limit).
- [x] `backend/print_chunks.py` printed and read locally (2026-10-31):
      109 documents -> 454 chunks, biggest 299 tokens. Cuts fall between
      paragraphs, no chunk starts mid-word, and the overlap repeats the last
      paragraph of one chunk at the start of the next. Jobs make 1–8 chunks
      (the 7 seeded samples are 1 each).
- Noted for Part 3: a chunk from the middle of a job description does not
  say which job it is from. Prefix each chunk with the document title when
  embedding.

### 3 — Embeddings and storage

**Status:** Complete (2026-11-02)

**Build:** a `chunks` table with `text`, `embedding vector(...)`, and metadata
(`user_id`, `doc_type`, `job_id`, `document_id`) via an Alembic migration; an
ingestion step that embeds each chunk and saves it; an HNSW index. Notes `02`,
`03`.

**Acceptance:** every document has chunks with embeddings; `EXPLAIN` shows the
HNSW index in use.

**Implementation checklist:**

- [x] `pgvector` Python package added; `chunks` table with `vector(1536)`, an
      HNSW index using cosine, and an index on `user_id` (migration
      `3518023b6e38`). `user_id`, `job_id` and `doc_type` are copied from the
      document so a search filters on this table alone.
- [x] The test database enables pgvector in `conftest.py`, because
      `create_all` does not run the migration that does.
- [x] `app/embed_chunks.py`: cuts every document, puts its title at the start
      of each chunk, embeds with `text-embedding-3-small`, 100 chunks per
      request, then replaces all chunks. A failed OpenAI call leaves the old
      chunks in place. `build_documents.py` deletes documents, which deletes
      their chunks, so run this after it.
- [x] Local run (2026-11-02): 454 chunks, 1536 numbers each, no document
      without chunks. `tests/test_embed_chunks.py` covers it with a fake
      OpenAI client.
- [x] HNSW check, accepted 2026-11-02 on two tests. On the real 454 rows,
      Postgres chooses a sequential scan and sort (about 6-7 ms); with
      `enable_seqscan` off it uses the index (about 2 ms) and returns the same
      5 chunks. On a temporary table of 20,000 random vectors it chose HNSW by
      itself, with and without a broad `user_id` filter (about 5 ms, against
      301 ms with the index off). Test the real search query again in Part 4,
      including a narrow filter, which can return fewer than 5 results.
- [x] Run on Render (2026-11-02): `build_documents.py` and
      `python -m app.embed_chunks` against the External Database URL. Checked
      with psql: Alembic at `3518023b6e38`, 107 documents, 473 chunks, 1536
      numbers each, no document without chunks. Render has more chunks than
      local (454) because its 100 imported jobs were fetched on a different
      day. No resumes or notes in production yet.

### 4 — First search

**Status:** Complete (2026-11-06)

**Build:** an endpoint that embeds a question and returns the top 5 nearest
chunks, always filtered by the current user. Notes `02`, `04`.

**Acceptance:** realistic questions return sensible chunks; a second user never
sees the first user's chunks (tested).

**Implementation checklist:**

- [x] `app/search.py`: `search_chunks` returns the 5 chunks closest to the
      question's vector by cosine distance, keeping only public chunks
      (`user_id IS NULL`) and the current user's own.
- [x] `app/routers/search.py`: `POST /search` with `{"question": "..."}`.
      The user comes only from the login token; the question is embedded
      with the same `embed` function as the chunks, then passed to
      `search_chunks`. The question is trimmed, and a blank one or one over
      1,000 characters is rejected (422).
- [x] Response schema `SearchResult`: `id`, `job_id`, `doc_type`, `content`.
      The embedding, `user_id` and `document_id` are not sent.
- [x] `tests/test_search.py`: 8 tests with made-up vectors and a fake
      `embed`, so no test calls OpenAI. They cover closest first, at most 5,
      public plus own chunks, another user's chunk never returned even when it
      is the closest (in the function and through the endpoint), the response
      fields, blank and huge questions, and a missing login (401).
- [x] Real questions, local database, real OpenAI (2026-11-06), one local
      user with a resume and a note:
      - "Which jobs use React and TypeScript?": the resume, then 4 React and
        frontend jobs. Good.
      - "Remote roles working on LLMs or AI agents": AI engineering and AI
        research jobs. Good.
      - "What experience do I have?": the resume first, then unrelated jobs.
      - "What should I ask in the TransPerfect interview?": the TransPerfect
        note first, then its job. Good.
      - "What did I note about my applications?": 5 unrelated jobs; the note
        is missed, because search matches meaning and the note is about
        TransPerfect, not about "notes".
- [ ] Narrow-filter check with HNSW: not done. On the local 454 rows Postgres
      sorts all rows even with `enable_seqscan` off, so the index is not
      used and the question (can a narrow filter return fewer than 5?) cannot
      be tested here. Repeat once there is more data.

**Follow-ups (not part of this acceptance):**

- A saved resume or note is not searchable until `build_documents.py` and
  `python -m app.embed_chunks` are run again. Update chunks automatically
  on save (candidate for Part 5).
- General questions about notes miss them. Possible fix: filter by
  `doc_type` when the question is about notes.
- Two chunks of the same job can both be returned. Possible fix: keep the
  closest chunk per job.
- `POST /search` calls OpenAI on every request and has no rate limit yet;
  chat has one. Add it before real users.
